## Verdict

**Loop Engineering is a pattern library for scheduled maintenance loops around a repository, with a set of small helper CLIs.** It names eight patterns, such as daily triage, PR babysitter, CI sweeper and dependency sweeper. For each it gives a cadence, a state file, a maker and checker pair of skills and a cost table, plus copy-paste prompts for Claude Code, Codex, Grok, OpenCode and others. The README calls it "a pattern library for operating agents around a codebase" ([README.md:50](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/README.md#L50)). The loop itself is someone else's scheduler, such as Claude Code's `/loop`, cron or GitHub Actions, running someone else's agent with these prompts.

**For Waymark: ignore it as a dependency. It does a different job and enforces less.** Loop Engineering finds work on a schedule and proposes small fixes. Waymark's factory takes one agreed change through holdout tests, a build, independent verification, bounded repair and two human decisions. Waymark's code already enforces most of the controls this repository recommends, and the repository mostly describes them in prompts and Markdown. They are a separate verifier, worktree isolation, attempt caps, per-run spending caps, human approval before merge, and measured cost. A halt and job budgets are planned in PR #57. Two of its ideas are missing from Waymark, a repeat-failure breaker and a rule for flaky checks, and neither justifies work now. See [Relevance to Waymark](#relevance-to-waymark).

**Borrow at most one idea, and not now.** `loop-context --check` is a small deterministic circuit breaker. It stops a fix loop when the same normalized error repeats, or the same action repeats, before the attempt cap runs out ([context-manager.ts:224-314](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/context-manager.ts#L224-L314)). Waymark's repair limit defaults to one, and its autopilot doesn't retry a failed step until the card changes. A repeat detector has nothing to catch at those limits. It becomes worth a ticket only if projects raise the repair limit and the planned repair pass count shows repairs failing the same way twice.

**Its own dogfood argues for Waymark's design.** The repository's one automated loop is a deterministic Node script that runs `gh` to read open issues and pull requests and writes `STATE.md`, in about ten seconds ([github-triage.mjs:1-9](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/scripts/github-triage.mjs#L1-L9), [267](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/scripts/github-triage.mjs#L267)). It calls no model. Its run log still records a constant `tokens_estimate: 52000` per run ([daily-triage.yml:110](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/.github/workflows/daily-triage.yml#L110)), while its own readiness score has stayed at 100, the top "L3 unattended" level. The maintainers wrote this up in August ([thirty-weekday-runs.md](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/stories/thirty-weekday-runs.md)). The placeholder is still in the workflow at the pinned commit. The Lulla et al. paper says observed run logs "hold template values, not measurements", and cites this repository. Waymark already says metrics are measured, not estimated. This is what happens when they aren't.

What it is, in brief:

- **Mostly prose.** 330 Markdown files with about 16,800 lines. Docs, patterns, skills and stories make up 5,400 of those lines, and the rest is starters and examples for each agent tool, plus issue bodies.
- **No loop runtime.** Sixteen TypeScript tools hold 11,690 source lines and 433 test cases, and a composite GitHub Action wraps two of them. None calls a model or starts an agent. They score which files exist, copy templates, check policy over JSON or YAML, and wrap `git worktree`. The loop is a `/loop` prompt that `loop-init` prints for the user to paste into their agent.
- **Safeguards are mostly unwired.** The circuit breaker and the merge gate are real code, but nothing in the repository calls either one. No code checks the `loop-pause-all` kill switch. The repository's own bots auto-merge their PRs under a ruleset that requires no review, while its constraints file says "Never auto-merge to main without human approval".
- **The readiness score counts files.** `loop-audit` awards its verifier points for any file whose name contains "verifier". The repository's own `loop-drill` says an empty file passes.
- **Popular and young.** Created 9 June 2026. 11,665 stars and 1,573 forks on the research date. Most human commits fell in June to August, and the maintainer's last commit was on 28 August. Since September, bots made 133 of 147 commits.
- **Cited by research.** Lulla et al. reviewed it as gray literature and drafted their detection heuristics from it. That makes it a reference for the vocabulary, not evidence that its patterns work.
- **Stories are weak evidence.** Ten of the 21 "production stories", including week-one accounts and a CI sweeper that burned eight million tokens, were committed on the day the repository was created, with no named project.

## How the patterns describe a loop

The vocabulary is Addy Osmani's five primitives plus memory. They are automations or scheduling, worktrees, skills, plugins and connectors, sub-agents as maker and checker, and an external state file ([primitives.md](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/docs/primitives.md)). The repository adds three things of its own.

**Readiness levels.** L0 is documented intent, L1 triage into state with no action, L2 small fixes with a verifier, and L3 unattended ([loop-design-checklist.md:84-87](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/docs/loop-design-checklist.md#L84-L87)). The README tells people to move up a level "only after the verifier has been right for a week" ([README.md:86](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/README.md#L86)). A "Loop Ready" score computed by `loop-audit` maps a repository to a level.

**A maker and checker in skills.** `minimal-fix` makes the smallest diff for one target and must not mark its own work done ([minimal-fix SKILL.md:47-52](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/skills/minimal-fix/SKILL.md#L47-L52)). `loop-verifier` rejects by default, reruns the tests itself, checks diff scope and looks for disabled tests. It returns APPROVE, REJECT or ESCALATE_HUMAN ([loop-verifier SKILL.md:21-47](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/skills/loop-verifier/SKILL.md#L21-L47)). Both are prompts. Whether the checker really is a separate agent depends on the harness and on whoever wires the loop.

**Policy files.** `gate.yaml` holds a path denylist, `maxFiles: 10` and an auto-merge allowlist ([gate.yaml](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/gate.yaml)). `loop-budget.md` holds token caps per loop, and `loop-constraints.md` holds rules. Every skill carries a generated "Untrusted input" section that treats issue, PR, comment and CI text as data, never instructions ([loop-verifier SKILL.md:50-60](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/skills/loop-verifier/SKILL.md#L50-L60)).

A typical fix-capable cycle, as the CI sweeper pattern describes it ([ci-sweeper.md:43-59](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/patterns/ci-sweeper.md#L43-L59)):

1. Discover failures on watched branches and classify them as flake, regression or infrastructure. A test that failed and then passed without a code change is a flake and isn't fixed.
2. Open a worktree and have an implementer draft a minimal fix.
3. Have a verifier check scope and intent and run the tests in the worktree.
4. Open a PR or comment. The implementer can't merge.
5. Before each retry, run `loop-context --check`. Escalate when the same failure repeats or attempts exceed a cap such as three.

The skill for step 5, `loop-guard`, isn't in `skills/`. It is a template that `loop-init` copies into a project for L2 patterns ([templates/SKILL.md.loop-guard](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/templates/SKILL.md.loop-guard)).

### The circuit breaker

`loop-context` is the one piece of code that acts inside a fix loop, and the one idea in the repository Waymark doesn't already have in some form. It reads a JSON ledger of attempts, each with an action, an outcome and an optional error and token count ([context-manager.ts:19-45](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/context-manager.ts#L19-L45)). `--check` exits 0 to continue and 2 to escalate ([cli.ts:162](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/cli.ts#L162)). It checks, in order:

| Rule | Fires when | Default |
| --- | --- | --- |
| Stagnation | The trailing failures share an error signature. The signature is the error's first non-empty line with timestamps, hex addresses, paths, line numbers and other numbers normalized away, compared by character-trigram Jaccard similarity | 3 in a row at similarity 0.85 or more |
| Frustration | The trailing failures describe a similar action | 3 in a row |
| No progress | Consecutive failures without a success | 5 |
| Token budget | The ledger's summed `tokensUsed` reaches the cap | off unless set |
| Iteration cap | Total attempts | 10 |

Sources: [context-manager.ts:71-77](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/context-manager.ts#L71-L77), [136-150](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/context-manager.ts#L136-L150), [224-314](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-context/src/context-manager.ts#L224-L314).

It is honest code with a weak input, and nothing in this repository calls it. In a project that adopts it, the agent being guarded writes the ledger, following the `loop-guard` skill's instructions. Nothing outside the agent records what the attempt did or what failed, so the breaker trusts the reports of the loop it is meant to stop. Its token cap works only if the agent reports its own tokens.

## The repository's own loops

`LOOP.md` lists the loops that maintain the repository. Its automation table shows which are automated ([LOOP.md:80-94](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/LOOP.md#L80-L94)). Only L1 loops run on their own. PR babysitter is manual, the dependency sweeper is Dependabot, and the CI sweeper has "no dedicated retry workflow".

`daily-triage.yml` runs on weekdays at 08:00 with write access to contents, pull requests, issues and commit statuses. In order, it builds `loop-audit` and scores the repository. Then it runs `scripts/github-triage.mjs`, which reads PRs and issues through `gh` and applies fixed rules for age, CI state and conflicts ([github-triage.mjs:120-210](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/scripts/github-triage.mjs#L120-L210)), and writes `STATE.md`. Last, it appends a run log line with constant token and action values, opens a PR, posts the `validate` and `audit` statuses that branch protection requires, and auto-merges the PR ([daily-triage.yml:183-220](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/.github/workflows/daily-triage.yml#L183-L220)). It runs inline gate checks first, and it only touches state, log and badge files. No model and no secret beyond the workflow token are involved.

The run log holds 22 runs from 30 September to 29 October, one per weekday, each taking 8 to 19 seconds ([loop-run-log.md:24-45](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/loop-run-log.md#L24-L45)). Fourteen are marked `escalated`. In this workflow that means the latest validate or audit run on `main` had failed ([daily-triage.yml:97-101](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/.github/workflows/daily-triage.yml#L97-L101)), not that an agent handed something to a person.

`changelog-drafter.yml` opens a "Release prep" issue with the last tag and asks a person to run the starter skills locally ([changelog-drafter.yml:20-86](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/.github/workflows/changelog-drafter.yml#L20-L86)). A star-history workflow commits an SVG daily. So the repository's automated loops are a cron job, an issue template and a chart. Nothing in its history shows a fix-capable loop from its own patterns running against it.

## Tests and CI

There are 433 test cases across `tools/*/test`, plus 36 in the root scripts. They test pure functions such as the gate, the breaker, the cost estimator and the mutation operators. They also run CLIs on temporary directories, create real Git worktrees, and do an MCP round trip over stdio. Every "agent" in them is a stub, such as a local `agent.cjs` or `node -e "process.exit(0)"` ([swarm.test.mjs:24](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-swarm/test/swarm.test.mjs#L24), [canary.test.mjs:50-115](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-drill/test/canary.test.mjs#L50-L115)). No test runs a model, and none runs a maker, verifier and retry loop end to end.

PR CI runs `validate-patterns.yml` and `audit.yml`. They grep the pattern Markdown for required headings and the word "verifier" ([ci-validate-gates.sh:20-25](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/scripts/ci-validate-gates.sh#L20-L25)), run most tool tests, run `loop-drill`, and require an audit score of at least 58 ([ci-audit-gates.sh:77-100](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/scripts/ci-audit-gates.sh#L77-L100)). Tests for `loop-cost`, `loop-worktree`, `loop-sandbox` and `loop-swarm` run only in their release workflows. The `loop-metrics` tests never run.

Fourteen release workflows publish to npm with provenance. Supply-chain notes for anyone who does run it:

- Packages are fetched at run time with unpinned `npx --yes`, and the examples pin `loop-action@main`.
- `loop-action` interpolates `${{ inputs.pattern }}` and `${{ inputs.level }}` directly into a shell command ([action.yml:36](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/tools/loop-action/action.yml#L36)).
- `fork-pr-gate.yml` marks the required checks green, without running them, for fork PRs that touch only content paths, and `skills/` counts as content ([fork-pr-gate.yml:50-91](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/.github/workflows/fork-pr-gate.yml#L50-L91)). Those skills ship as a Claude Code plugin. With no required review, the maintainer's merge click is the only control on them.
- No install-time scripts and no `curl | sh`.

## External sources

The README lists three sources ([README.md:120-125](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/README.md#L120-L125)). All three were read on the research date.

**Addy Osmani, [Loop Engineering](https://addyosmani.com/blog/loop-engineering/), 7 June 2026.** This is where the term and the "five primitives plus memory" come from. The page describes Osmani as working on Claude Code at Anthropic. It maps each primitive to Codex and Claude Code features and walks through one daily loop: a morning triage writes findings to a file, a sub-agent drafts a fix in a worktree, a second sub-agent reviews it, and connectors open the PR. It argues hard for separating the writer from the checker. It gives no retry limits and no approval gate before merge. Stop conditions appear only through `/goal`. It doesn't mention this repository.

**Cobus Greyling, [Loop Engineering](https://cobusgreyling.substack.com/p/loop-engineering), 9 June 2026.** This is the companion essay, published the day the repository was created. It credits Osmani with the framing and doesn't claim the term. It cites Peter Steinberger and Boris Cherny, and it warns that sub-agents and short cadences multiply token cost. It links the repository as the practical reference but says nothing about its contents.

**Lulla, Nersesyan, Mohsenimofidi, Treude and Baltes, [Loop Engineering: Building Blocks, Adoption, and Impact](https://arxiv.org/abs/2608.21884), arXiv 2608.21884v3, 22 October 2026.** The README says "this repo is the community reference they reviewed". That holds. The paper reviews gray literature that includes a snapshot of this repository from 15 July and the essay. It says the authors "drafted the heuristics and thresholds from Greyling's repository" for their mining study (§4.1). Its findings matter more than the citation:

- The practitioner sources agree on the building blocks. The paper adds that they aren't independent: Greyling's repository and another playbook "explicitly build on Osmani's posts", so much of the agreement "traces back to one origin" (§3).
- The sources offer no systematic evidence of benefit. The boldest figures are self-reported (§3).
- Of 36,487 repositories analyzed, 217 had autonomous agent loops. None had a confirmed committed loop state file. No verifier or budget showed up as a committed artifact. Verifiers and spending or turn limits appeared only when the authors annotated Claude Code sessions (RQ2).
- On cost, the paper's own table says observed run logs "hold template values, not measurements" and cites this repository.
- The controlled experiment is a design. It hasn't been run.

So the strongest outside evidence about "loop engineering" says the idea is coherent, widely repeated and almost entirely unmeasured.

`resources/sources.md` also points to [open-spek/loop](https://github.com/open-spek/loop), which it calls a different use of the same term: a test-gated, fresh-context loop that builds a frozen specification into a verified implementation one milestone at a time ([sources.md:47-48](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/resources/sources.md#L47-L48)). By that description it is closer to Waymark's job than this repository is. It wasn't read for this note.

## Relevance to Waymark

The two projects share words, not a job. Loop Engineering's loops find work on a schedule and keep a repository tidy, and they stop at a proposed PR that a person merges. Waymark's factory starts from one agreed work item and carries it to a verified merge. The comparison below runs along Waymark's loop. "Waymark" means `dev` at `afe9989` and, where stated, the plans in [PR #57](https://github.com/Zokiio/context/pull/57) (`feat/factory-gap-plans` at `44e1379`).

| --- | --- | --- |
| Intake | Daily and issue triage write a queue into `STATE.md`. Skills treat tracker text as untrusted data. | Nothing new. The intake plan already polls trackers, marks imported text in prompts, and requires a person to agree what done means before any agent with write or command tools reads it ([intake spec](https://github.com/Zokiio/context/blob/44e137962ca364bdf215f381509cbb7084b56921/.scratch/factory-intake/spec.md)). |
| Refine | Nothing. A queue line "should be small enough for one PR" ([refactor.md:35](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/docs/refactor.md#L35)). | Nothing to borrow. |

Waymark protects tests and fixtures from the implementer and fails a candidate that touches them ([factory-platform-design.md:29](../factory-platform-design.md), [73-75](../factory-platform-design.md)). |

**The orchestrate skill.** Its checkpoint loop already says to "diagnose or escalate a repair loop that stops producing new evidence or reducing known failures" ([orchestrate SKILL.md:59](../../.agents/skills/orchestrate/SKILL.md)). The orchestrator reads the retained evidence files itself, so it has better input than a self-reported ledger. Workers already start in fresh context, and the runner and both reviewers are separate. Loop Engineering adds nothing here.

**Bounded repair.** The one idea worth keeping on file is the stagnation rule. Waymark's limit counts repairs. It doesn't notice that the last two repairs failed the same check with the same first error line, which is the signal that a third will too. In Waymark the input would be honest: the service already retains each failed check's key, command and log, and the planned repair brief carries them forward ([repair brief ticket](https://github.com/Zokiio/context/blob/44e137962ca364bdf215f381509cbb7084b56921/.scratch/records/factory-harnesses/issues/01-repair-brief.md)). At today's settings it would never fire. The default limit is one, and the autopilot never retries a failed step until the work item changes ([pilot.go:13-17](../../internal/factory/pilot.go#L13-L17)). Revisit it if projects raise the limit and the planned repair pass count shows repairs failing twice on the same signature ([repair pass count ticket](https://github.com/Zokiio/context/blob/44e137962ca364bdf215f381509cbb7084b56921/.scratch/records/factory-harnesses/issues/02-repair-pass-count.md)).

**One gap it points at, without a mechanism.** The CI sweeper won't fix a test that failed and then passed with no code change ([ci-sweeper.md:57-59](https://github.com/cobusgreyling/loop-engineering/blob/18b16342aca27b40f3cac0bb0ab42b7df3ee2cd1/patterns/ci-sweeper.md#L57-L59)). In Waymark, a failed required check fails the job, and the next step is a repair. Neither the factory documentation, the design, nor the PR #57 plans mention flaky checks, and the factory code doesn't rerun a failed check. A flaky check therefore spends the job's only repair on a defect that isn't there. The repository offers a sentence of prose, not a mechanism. Whether this needs handling is a question for trial data.

**Don't take.** The Loop Ready score, which rates files on disk. The `budget-negotiator` skill, which has the agent argue for more budget. The auto-merge allowlist for test files. The unattributed stories as evidence.

## Evidence and limitations

- **Read, not run.** The repository was cloned into an empty scratch directory and read with `git`, `cat`, `sed` and `grep`. No package was installed or built, no test, script or workflow was run, and no `npx` command was executed. Test files show what is asserted, not that it passes.
- **Coverage.** The README, `LOOP.md`, the concept, primitives, refactor and checklist docs, the CI sweeper pattern, the verifier, minimal-fix and budget-negotiator skills, the `loop-guard` template, `gate.yaml`, the daily triage workflow, the run log and the cited stories were read in full. All `tools/*/src` files and tests and all workflows were read by a research agent and its key claims were rechecked by hand at the pinned commit. Starters, examples per tool, the remaining patterns and docs, and `scripts/issue-bodies/` were read by search only.
- **History and metadata.** Commit counts come from the clone's history. Stars, forks, releases and contributor counts come from the GitHub API, and npm versions from the registry, all on 29 October 2026. GitHub's contributor counts merge co-authored and squashed work differently from `git log`, so the two don't add up exactly.
- **External sources.** The three linked sources were fetched and hashed on the research date. The paper was read in its HTML rendering of v3. Its statements are quoted from that version.
- **Not checked.** Whether the npm tarballs match the repository source. Whether any adopter in `docs/adopters.md` runs these patterns. The sibling repositories, and `open-spek/loop`.
- **Waymark side.** Statements about Waymark come from `dev` at `afe9989` and the PR #57 plans at `44e1379`, listed under `local_sources` in the ledger. Nothing in Waymark was changed or run for this note.
