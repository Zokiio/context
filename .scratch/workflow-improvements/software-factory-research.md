## How the projects relate

StrongDM publishes Attractor as three natural-language specifications for others to implement. Its README tells the reader to hand the repository to a coding agent ([README](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/README.md#L3-L19)).

Fabro credits Attractor as its inspiration and Kilroy as a reference ([acknowledgements](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/reference/acknowledgements.mdx#L8-L10)). Its Definition of Done example audits an implementation against Attractor's own spec files ([example](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/examples/definition-of-done.mdx#L28)). Its workflow engine and DOT frontend now come from external `lithoscomputer/petri` crates, including one named `petri-frontend-attractor` ([Cargo.toml](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/Cargo.toml#L105-L115)).

Lightspeed began as "Forge", an implementation of the Attractor specs ([README at an early commit](https://github.com/smartcomputer-ai/lightspeed/blob/22b39800f16153f09e2efc53fd5ee0ab577a59ee/README.md#L1-L5)). Later roadmap phases put Attractor integration out of scope and listed "No Attractor rebuild" as a non-goal ([P40](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/docs/roadmap/archive/p40-new-agent-core.md#L238-L247), [P46](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/docs/roadmap/archive/p46-rework-agent.md#L1529-L1538)). Nothing of Attractor remains in it.

CodeAF and SWE-AF both come from AgentField and both depend on the AgentField Go SDK ([CodeAF go.mod](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/go.mod#L8)). SWE-AF runs as a node on the AgentField control plane, and its Go port is now the installed node ([Go README](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/go/README.md#L1-L22)).

Superplane and Open-Inspect (`background-agents`) are unrelated to Attractor. Open-Inspect describes itself as inspired by Ramp's Inspect ([README](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/README.md#L5-L6)).

## StrongDM's factory site and Attractor

The site defines a software factory as non-interactive development in which specs and scenarios drive agents that converge without human review. Its rules are that humans neither write nor review code ([factory.strongdm.ai](https://factory.strongdm.ai/)). It replaces in-repo tests with "scenarios": end-to-end user stories kept outside the codebase like a holdout set and judged by an LLM. "Satisfaction" is the fraction of observed scenario trajectories judged to satisfy the user. A "Digital Twin Universe" of cloned third-party services supports high-volume validation ([same page](https://factory.strongdm.ai/)). The loop runs until holdout scenarios pass ([principles](https://factory.strongdm.ai/principles)). Non-interactive runs are reserved for work whose intent is already complete, such as an RFC with a test suite ([shift work](https://factory.strongdm.ai/techniques/shift-work)).

The Attractor spec defines a pipeline runner over a strict subset of Graphviz DOT. Node shapes map to handlers: LLM task, human gate, conditional, parallel fan-out and fan-in, shell tool, and supervisor loop ([spec §2.8](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L179-L193)). Traversal is single-threaded. Edge selection is a deterministic five-step algorithm over conditions, preferred labels, suggested IDs, weights, and node IDs ([§3.3](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L406-L418)). A JSON checkpoint is written after every node ([§5.3](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L1096-L1134)). Human gates present outgoing edge labels as choices ([§4.6](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L720-L777)). How a stage calls an LLM is left to the implementer, including spawning Claude Code or Codex ([§1.4](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L54-L60)). Sandboxing and approval systems are out of scope ([agent loop §8](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/coding-agent-loop-spec.md#L1133-L1145)).

Verification in the spec is stage status. Nodes marked `goal_gate` must end in success or partial success before the pipeline may exit ([§3.4](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L461-L478)). The LLM handler returns success whenever the backend returns text, and any external agent may write the stage's `status.json` ([§4.5](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L656-L709)). Context is the run's key-value state, carried into the next stage at a chosen "fidelity" from full history to short summaries ([§5.4](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/attractor-spec.md#L1136-L1175)). Project knowledge enters through `AGENTS.md` and provider-specific instruction files, capped at 32 KB ([agent loop §6.5](https://github.com/strongdm/attractor/blob/fb57a55ed97372a27ac90102f436947e29f48426/coding-agent-loop-spec.md#L1040-L1056)).

Where the site goes beyond the published code:

- The product page calls Attractor StrongDM's implementation and links to the repository ([product page](https://factory.strongdm.ai/products/attractor)). The repository holds only the three specs, and none of its 15 commits ever added implementation code.
- The product page says edges are expressed in natural language and evaluated by the LLM. The spec selects edges deterministically from the stage's returned outcome. The model influences routing only through the label or node IDs it reports.
- Scenarios, satisfaction, holdouts, and digital twins do not appear in any of the three specs. The site's validation method has no published implementation in this repository.
- The community list is stale. "Forge" is now Lightspeed and has dropped Attractor. Fabro is described with automatic retrospectives, which Fabro removed ([plan](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/plans/2026-05-08-remove-retro-stage-plan.md#L3-L5)).

Verdict: Attractor is a design reference for an agent runtime, not software to integrate with. Its evidence is a stage reporting its own status. The rule that "Code must not be reviewed by humans" is the opposite of our review default. Only the holdout idea matches a Waymark concern: keep the expectations an agent is judged against out of that agent's reach.

## Fabro

Fabro describes itself as an open-source dark software factory ([README](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/README.md#L5)). Work is a `.fabro` Graphviz workflow plus optional run configuration ([how Fabro works](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/core-concepts/how-fabro-works.mdx#L21-L28)). The engine walks the graph through agent, command, human, and parallel handlers and checkpoints after every stage ([execution loop](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/core-concepts/how-fabro-works.mdx#L38-L66)). It runs as a CLI or a server with a web UI. Run history lives in a server SQLite database ([server configuration](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/administration/server-configuration.mdx#L262-L266)).

Bundled sandboxes are `local` with no isolation, Docker, and Daytona VMs. Other providers plug in through `sandbox-driver` ([sandboxing](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/administration/sandboxing.mdx#L8)). Stages can use Fabro's own agent loop or an external agent over the Agent Client Protocol ([agents](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/core-concepts/agents.mdx#L19-L66)). After each stage, Fabro commits changes to a `fabro/run/{run_id}` branch, and the checkpoint event records that commit SHA ([checkpoints](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/execution/checkpoints.mdx#L8-L39)). A local-folder run works in a clone of committed `HEAD`, so uncommitted changes are excluded ([same page](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/execution/checkpoints.mdx#L6)).

A command stage succeeds on exit code 0. An agent stage succeeds unless the model's own routing directive says otherwise ([outcomes](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/execution/outcomes.mdx#L27-L28)). Goal gates fail the workflow when a marked stage did not succeed ([same page](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/execution/outcomes.mdx#L109-L120)). The Definition of Done example has LLM audits emit JSON pass or fail per spec checkbox, then runs build and test gates and ends at a human gate ([example](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/examples/definition-of-done.mdx#L259-L271)). Agent context is the node prompt, a fidelity summary of earlier stages, and `AGENTS.md` or `CLAUDE.md` found between the Git root and the working directory ([prompts](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/agents/prompts.mdx#L263-L272)).

Fabro's own documents contain a verification gate that cannot fail. The branch-loop tutorial appends `|| true` to its test command so the stage always succeeds. It then routes to exit on success ([tutorial](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/tutorials/branch-loop.mdx#L24-L58)). The NLSpec conformance example puts `goal_gate=true` on such a command while claiming the gate fails the run if conformance never passes ([example](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/docs/public/examples/nlspec-conformance.mdx#L51-L130)). Under the documented outcome rule, both gates always pass. I did not run Fabro to confirm the runtime behavior.

A GitHub and Linear `Tracker` trait exists ([source](https://github.com/fabro-sh/fabro/blob/9d9cbe9f417006603a4bbc4372ffdb2477afa314/lib/components/fabro-tracker/src/lib.rs#L101-L118)), but no other crate references it at this commit.

Verdict: Fabro is a runtime we would integrate with, not build. It is the most usable piece of the Attractor lineage. It competes with our skill-based orchestrator trial, not with project records. It has no notion of criteria. Its evidence is stage status plus a commit SHA. The per-stage commit is the useful part: every stage output is tied to a code revision.

## Lightspeed

Lightspeed is infrastructure for running fleets of managed agents as durable workflows ([README](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/README.md#L17)). Its Rust core runs on Temporal with Postgres and optional S3 ([README](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/README.md#L29-L30)). It replays an event-sourced session log to decide each step ([README](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/README.md#L157)). The building blocks are sessions, profiles, files in a virtual filesystem, machines attached on demand, and event-triggered bots ([concepts](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/docs/documentation/getting-started/concepts.md#L82-L127)). The README's "software factory" is a seeded web demo ([fixture](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/platform/web/src/demo/fixtures/software-factory.ts#L1-L8)). Human approval covers MCP tool calls only ([tools](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/docs/documentation/how-it-works/tools-and-controller-workflows.md#L72-L82)). I found no work-item, acceptance, or verification concept.

Context assembly is the one overlap. Before a run, Lightspeed refreshes prompt sources from attached workspaces and records an assembly report. The report shows where instructions came from and which sources were omitted. An oversized source is omitted whole rather than truncated ([context and storage](https://github.com/smartcomputer-ai/lightspeed/blob/86f6adf3cd28cde11644403c886ae08324cf21bb/docs/documentation/how-it-works/context-and-storage.md#L85-L117)).

Verdict: irrelevant to our milestones. It is a runtime we would integrate with only if we ever needed long-lived agent fleets, and the Temporal and Postgres footprint is far from local-first. Its whole-source omission rule matches our reader's rule from another direction.

## Superplane

Superplane's README says it turns backlog issues that agents can handle with high confidence into verified, review-ready pull requests ([README](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/README.md#L24-L36)). The factory sits behind an experimental `factories` flag ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L5)). All state is in PostgreSQL ([architecture](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/contributing/architecture.md#L21-L23)).

A work order has a title, description, and assignees. Its states are `draft`, `open`, and `closed`, and closing requires a result ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L12-L16), [model](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/pkg/models/factory_work_order.go#L19-L28)). The draft PRD's `ready` and `successful` states are superseded by the code. A line is an ordered list of canvas-app steps. Dispatch runs step 0, advances only when a run passes, and allows one active execution per work order per line ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L21-L27)). Intake can create work orders from GitHub, Jira, and Linear issues, Sentry, PagerDuty, Dependabot, and Datadog ([intake](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/pkg/models/factory_intake.go#L15-L22)). The design doc still lists external intake as unimplemented ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L407-L413)), so that section is stale. Plans travel as `intent.md` and `plan.md` artifacts ([source](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/web_src/src/pages/factories/lib/intentDocument.ts#L1-L5)). There is no acceptance-criteria field.

The readiness-like judgment is LLM-scored. The refinement skill scores Clarity, Complexity, and Verifiability from 1 to 3, and Confidence is the weakest of the three ([skill](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/.agents/skills/refine-task-workflow/SKILL.md#L12), [rubric](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/.agents/skills/refine-task-scoring/SKILL.md#L54-L60)). The scores are advisory. The UI lets a user start during analysis or accept a low score as a risk ([UI copy](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/web_src/src/pages/factories/lib/draftReadiness.ts#L38-L53)). Each check keeps only its latest score in a row, and every report is also appended to the work order's event history ([model](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/pkg/models/factory_work_order_check.go#L47-L50)).

Evidence is bound to pull-request revisions. Each observed head SHA becomes a revision. Check handlers wait for GitHub checks on one revision and start an agent when selected checks fail. One activity at a time can hold exclusive access to change a pull request, while others wait concurrently ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L134-L136)). The PRD says success is an explicit operation, not inferred from pull-request state ([PRD](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/prd/software-factory.md#L214-L218)). The line metrics count a merged pull request as a success anyway ([design](https://github.com/superplanehq/superplane/blob/1be6b59d8c884084457c0bb3248580e173115822/docs/design/factory.md#L169)).

Verdict: this is the closest product overlap. It has a durable work record with append-only history, a pre-dispatch readiness judgment, and CI evidence keyed by revision. The authority model is the opposite of ours. A server database is authoritative, readiness is a score users can click past, criteria are absent, and merges count as success. It is a competitor for the team-pilot story and irrelevant to local-first solo use. The Verifiability dimension is worth borrowing as an advisory observation.

## Open-Inspect (background-agents)

Open-Inspect is a hosted background coding agent for single-tenant deployments ([README](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/README.md#L5-L30)). Its control plane runs on Cloudflare Workers, and sessions run on Modal, Daytona, E2B, Vercel, or Boat sandboxes ([how it works](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/HOW_IT_WORKS.md#L183-L229)). Each session uses one harness, either OpenCode or the Claude Agent SDK ([same doc](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/HOW_IT_WORKS.md#L538-L552)). Work arrives as prompts from the web UI, Slack, GitHub, Linear, or automations. Verification is whatever the agent runs, including Playwright, followed by a pull request under the user's identity for normal review ([same doc](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/HOW_IT_WORKS.md#L562-L590)). I found no criteria or acceptance model.

Context provenance is careful. Managed skills are pinned at session creation, and the session shows each skill's revision, content digest, and reason for matching ([managed skills](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/MANAGED_SKILLS.md#L264-L275)). Memory written by an agent is a proposal until a human approves it. Budgeted selection omits whole records, counts them, and hashes the selected record, revision, and inclusion tuples ([memory](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/MEMORY.md#L8-L20), [selection](https://github.com/ColeMurray/background-agents/blob/776c771acf9e5fd389722f3506ea8587e22a54de/docs/MEMORY.md#L95-L119)).

Verdict: a hosted runtime, irrelevant to project records. Its skill and memory provenance confirms choices Waymark already made: digests and reasons for included sources, and proposed observations kept separate from adopted guidance. There is nothing to integrate now.

## CodeAF

CodeAF is a local terminal agent and task scheduler in one Go binary ([README](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/README.md#L42)). A message can become several tasks, each in its own copy of the repository and on its own branch ([README](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/README.md#L97-L112)). Work that passes its check lands on the user's branch, never `main`. Unchecked work waits for the user to accept it. State is an append-only event graph in SQLite under `~/.codeaf`, with atomic claims ([architecture](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/ARCHITECTURE.md#L11-L50)). Memory is recalled from earlier task digests by keyword search ([Decision 6](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/ARCHITECTURE.md#L146-L160)), and `AGENTS.md` files are read ([source](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/internal/seniordev/session/instruction/instruction.go#L140)). Model-measurement telemetry is on by default ([README](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/README.md#L193-L196)).

Its acceptance discipline is the strictest in this set. A task's brief and acceptance freeze at admission. A correction needs a new admission by the person, because an acceptance that can move during the work cannot judge it ([design](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/CHAT-V3.md#L878-L891)). For an unattended session, the model writes one done-condition for the whole request. The code writes it once and never again ([source](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/internal/session/principal.go#L1008-L1016)). Before an unattended session may finish, it reruns the declared checks from clean in a fresh process. Commands in prose and worker receipts do not count ([architecture](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/ARCHITECTURE.md#L279-L299)). Headless output distinguishes `failed` from `unverified`. A field appears exactly when nothing checked the work, and every acceptance point is reported as answered, not answered, or not reached ([headless](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/HEADLESS.md#L266-L270)). A separate package discovers the project's build and test commands and compares failing test names before and after ([source](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/internal/verify/discovery.go#L1-L15)).

The documents change quickly. One design was superseded on 2026-10-10 ([standing orders](https://github.com/Agent-Field/CodeAF/blob/c740a5417230dcabe074c7a7919c3403a44ebc79/docs/STANDING-ORDERS.md#L3-L12)).

Verdict: this is the closest philosophical overlap on verification integrity. It is still a runtime with its own store outside the project, and its acceptance is written by a model rather than agreed by a person. It is a plausible local runtime for a solo user later. Borrow the frozen-acceptance and clean-rerun discipline, not the store.

## SWE-AF

SWE-AF takes a goal and a repository and returns a draft pull request ([README](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/README.md#L33)). A product-manager agent writes a PRD with acceptance criteria. Architect and tech-lead agents follow, and a sprint planner decomposes the work into an issue DAG. Each issue carries criteria, file lists, testing guidance, and a risk rationale ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L63-L98)). Issues run in parallel git worktrees, a merger agent integrates them, and state is checkpointed to JSON ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L203-L213), [checkpoint](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L269)). A plan-approval gate exists only when an external HITL service key is set ([config](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/swe_af/execution/schemas.py#L1040-L1043)).

A verifier agent checks each PRD criterion against the codebase and feeds failures to a fix loop ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L53)). A criterion result holds the criterion, a pass flag, free-text evidence, and an issue name, with no revision ([schema](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/swe_af/execution/schemas.py#L455-L470)). The coder's test result is self-reported ([schema](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/swe_af/execution/schemas.py#L485)). When a coding loop fails, an advisor agent may relax the criteria or accept the issue with debt and mark it complete ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L155-L176)). An exhausted architecture review auto-approves the last revision ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L73)). A crashed replanner defaults to continuing. Debt is typed and severity-rated, propagated to dependent issues, and listed in the PR body ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L217-L239)).

The architecture doc says every agent action is cryptographically attested by AgentField ([architecture](https://github.com/Agent-Field/SWE-AF/blob/4d3dfe719e5ce9e2e8cd454722295bbe6512542f/docs/ARCHITECTURE.md#L3)). SWE-AF's own code contains no credential logic. The claim depends on the AgentField control plane, which I did not examine.

Verdict: this is the autonomy model our vision rejects. Agents write the criteria, relax them, and approve their own way past stuck reviews. Borrow the shape of its debt record and its per-criterion result. Avoid its control policy.

## Where this touches Waymark

**Context assembly.** The vision scopes context to the project and task, and included records carry revisions and a reason for inclusion ([vision](../../docs/vision.md#product-constraints)). `ctx context` already returns each source's SHA-256 and reasons, includes whole files within limits, and reports omissions ([reader reference](../../docs/readers.md#context-json-contract)). Only Lightspeed's assembly report and Open-Inspect's skill panel offer comparable provenance. None of the seven follows authored spec, context, and blocker links. Attractor and Fabro carry run state between stages. SWE-AF and Superplane hand agents a generated spec. My read: none of these replaces our reader, and the gap Waymark targets is real.

**Readiness.** Our readiness requires explicit criteria, available context, satisfied dependencies, and no blocking decision, and it is separate from pickup triggers ([vision](../../docs/vision.md#integration-progression)). Superplane is the only project with a readiness judgment before dispatch. It is an LLM score the user can override, and its intake sources play the role of pickup triggers. CodeAF freezes acceptance at admission but has no readiness gate. Fabro, Attractor, and SWE-AF start whenever invoked. My read: keep readiness deterministic. Superplane's Verifiability question fits beside readiness as an advisory observation, not inside it.

**Acceptance evidence.** The vision ties evidence to criteria and the tested revision, shows untested criteria, and separates workflow state from readiness ([vision](../../docs/vision.md#verification-and-development-deployment)). Our acceptance procedure already records per-criterion results, the tested revision, the deciding actor, separate human approvals, and requirement fingerprints ([acceptance](../../docs/agents/acceptance.md), [ADR 0003](../../docs/adr/0003-recorded-acceptance-for-readiness.md)). No surveyed project fingerprints the requirements an acceptance judged. SWE-AF records per-criterion LLM verdicts without a revision. Fabro ties stage status to a commit. Superplane keys CI results to a PR head SHA. CodeAF freezes acceptance and reruns checks from clean. My read: Waymark's acceptance model is already ahead. CodeAF's clean rerun and Superplane's revision-keyed CI results are the two mechanics worth taking, the latter for the later GitHub evidence adapter.

**Work claims.** The vision has one active implementation claim per work item, with reviewers working under it, and local exclusivity first ([vision](../../docs/vision.md#work-claims)). Superplane allows one active execution per work order per line and separates exclusive from concurrent pull-request activities. CodeAF uses atomic claims in one SQLite database per host. Fabro and SWE-AF isolate by worktree instead of claiming. My read: Superplane's exclusive-versus-concurrent split confirms the vision's claim model. No change is needed.

**The deferred agent runtime.** The vision keeps execution inside existing agent environments and defers a custom runtime ([vision](../../docs/vision.md#agent-execution-model)). Six of the seven projects are runtimes. Building another would duplicate Fabro, CodeAF, or Lightspeed. If the deferral ends, integrate rather than build. Fabro is the first candidate because its workflows are files in Git and its command stages could call `ctx`. One conflict is already visible: Fabro's local-folder runs see only committed `HEAD`, while our reader deliberately reads uncommitted record edits ([vision](../../docs/vision.md#first-milestone)).

## Practical inspirations to trial

1. **Guard expectation files mechanically.** StrongDM keeps scenarios outside the codebase so agents cannot rewrite them. CodeAF freezes acceptance for the same reason. The trial already has an independent expectation author ([choice 16](orchestration-design.md#confirmed-choices)). Add one gate: the diff from the expectations commit to the candidate, limited to expectation paths, must be empty unless the orchestrator recorded an approved change. The existing fixture can test this.

2. **Rerun acceptance checks in a clean worktree at the tested revision.** CodeAF's terminal audit ignores worker receipts and reruns declared checks in a fresh process. Our procedure permits a source digest manifest when a commit does not identify the tested tree ([acceptance](../../docs/agents/acceptance.md#complete-or-reassess-a-work-item)). For one ticket, run the checks in `git worktree add` at the tested commit and record that run as evidence. If the cost is small, prefer it in the procedure.

3. **Record during grooming how each criterion will be observed.** Superplane scores Verifiability, and SWE-AF issues carry testing guidance. Readiness stays unchanged. For two tickets, note per criterion whether it will be checked by a test, a command, a manual check, or a device. At acceptance, compare that with the criteria that ended untested. This extends [Helix proposal 3](helix-research.md#practical-inspirations-to-trial).

4. **Record an unmet criterion as a typed revision proposal, never as a relaxation.** Keep SWE-AF's debt fields: criterion, kind, severity, justification, and affected dependents. Route the record to the user as the vision's proposed revision of commitments. The ticket stays incomplete until the user decides. The orchestrate skill's escalation path can test it.

5. **Later, only if the runtime question reopens: probe Fabro with one command stage that calls `ctx context`.** Fail the stage on exit status 1, and commit the records first. This tests whether our JSON contract is enough for an external runner. It is not current work.

## What would contradict the vision

- Letting an agent relax, drop, or rewrite criteria, or mark work complete with known gaps, as SWE-AF's advisor does. Agents propose revisions and humans decide, and partial acceptance cannot satisfy a prerequisite ([vision](../../docs/vision.md#problem-and-responsibility), [acceptance profile](../../docs/agents/acceptance.md#acceptance-profile)).
- Approving automatically when a review loop is exhausted, or continuing after an orchestration failure. Our trial escalates stalled repairs instead ([choice 12](orchestration-design.md#confirmed-choices)).
- Dropping human code review as a rule, as StrongDM does. The vision defaults to teammate approval and a user merge ([vision](../../docs/vision.md#review-merge-and-completion)).
- Treating a stage's self-reported status as completion evidence: Attractor's default success, Fabro's agent outcomes, and SWE-AF's self-reported tests. Evidence keeps its origin and revision.
- Replacing readiness with a confidence score users can click past, as Superplane does. Readiness reports unmet conditions, and a score can only be advisory.
- Counting a merged or closed pull request as success. The vision evaluates completion against criteria after merge and does not require a pull request.
- Making a server or runtime database authoritative for work records: Superplane's PostgreSQL, Fabro's SQLite run store, CodeAF's `~/.codeaf`, Lightspeed's Postgres. Authoritative records stay in the record store, and caches stay disposable.
- Building a graph workflow engine or managed agent runtime into the Go core now. The vision defers it.
- Adopting model-written acceptance criteria without human agreement, as with CodeAF's unattended sessions or SWE-AF's product-manager agent. Agent-drafted criteria are acceptable only as grooming proposals.
