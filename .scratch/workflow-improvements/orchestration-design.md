## Confirmed choices

These choices record the user's answers during the design interview. The user refined the checkpoint definition, established project files as the primary store, and then required individual checkpoint files to limit the implementing agent's context. The trial scope is recorded below.

1. Prioritize easier review. A small result should present its intended behavior, changes, and evidence together. Use that experience to judge where more autonomy is justified. Reduced interruptions and repeated corrections remain possible benefits, rather than the first trial's primary goal.
2. Keep the existing execution boundary for the first trial. Skills and agent environments run the correction loop. `ctx` supplies project records and evaluations. Reconsider execution supervision only after identifying a failure of that arrangement. This confirms the existing [agent execution model](../../docs/vision.md#agent-execution-model).
3. A checkpoint is a small, reviewable part of a ticket's implementation plan, with a stated outcome and required checks. Its implementing agent needs the checkpoint's scoped context and gate demands, without loading or understanding the full implementation plan. Completing a checkpoint records progress. Acceptance still covers the whole work item. The [glossary](../../CONTEXT.md) owns the definition. Begin with the smallest checkable foundation, respect dependencies, and test uncertain assumptions early. Later checkpoints can grow as earlier decisions hold up.
4. Unmet criteria, violated documented constraints, and demonstrated defects block progress. Uncertain correctness concerns require investigation. A preference requires an explicit decision before it becomes a new requirement.
5. Retain feedback immediately with its source and scope. Adopt reusable conclusions into project guidance explicitly. Retention alone does not create a broader obligation for future work.
6. Specs, implementation plans, and checkpoints live primarily in durable project files in the application repository or the project's record store. Each document has one authoritative home. Tickets can link to these documents. The previous proposal to make ticket Comments their primary home is superseded. This follows the existing [record-location choices](../../docs/vision.md#independent-configuration-choices).
7. Verify each checkpoint's stated outcome and run independent standards and specification reviews. Include visual or environment checks when the outcome requires them. Corrections require affected checks and review of the changed code again.
8. For the first trial, the user reviews the initial plan and each checkpoint after its checks pass. The agent handles repair attempts. Decisions outside agreed scope or verification that cannot proceed reach the user earlier.
9. Review explicitly identified local commits. Corrections produce new code revisions for verification and review. A commit identifies the examined code; acceptance remains separate.
10. Keep the spec and implementation plan as separate documents, with one plan per work item. Each checkpoint has its own file, linked from the plan. The user rejected embedding all checkpoints in one plan file because the implementing agent should receive only its checkpoint and the context needed to satisfy its gates. Keep progress observations and verification evidence separate from the agreed plan and checkpoint requirements.
11. The orchestrator may split or reorder checkpoints while preserving agreed outcomes, dependencies, architectural constraints, and verification obligations. Record the change and reason. An implementing agent reports discoveries that require a plan change to the orchestrator. For changed commitments, assess impact and existing authorization as described in choice 17 before deciding how to revise the plan. A change to agreed goals or architectural boundaries still requires a human decision, but an already authorized change need not be approved again.
12. If a required check is unavailable, keep the checkpoint unverified and explain what is missing. Continue only work that does not depend on the unverified result. Escalate unavailable checks or repair attempts that stop making progress. The ticket remains unfinished until its required verification is satisfied.
13. Use an orchestrator to retain the full spec and plan, coordinate checkpoint assignments and verification, and manage the correction loop. The user endorsed this role after reading the video comparison, resolving Q14. For the first trial it runs through a skill in the existing agent environment, consistent with choice 2. Each implementing agent receives fresh context for its checkpoint. The existing first-trial human review policy in choice 8 still applies.
14. Give the implementing agent the checkpoint file, relevant requirements and architectural constraints, dependency contracts, starting code revision, and gate demands with their evidence expectations. Preserve authoritative source references. Missing required information goes to the orchestrator for focused additional context. The agent must not need to reconstruct the full plan.
15. The orchestrator commissions an independent review of the combined result against the full ticket and spec, with required integration checks, before ticket acceptance. Checkpoint results supply evidence but do not establish the whole outcome on their own.
16. The orchestrator delegates gate expectations and test preparation to an agent separate from implementation. That agent derives expectations from agreed requirements before implementation begins. Any proposed change to expected behavior must be justified against those sources. Independent check results retain the actual observing actor and code revision. The user accepted choices 14 through 16 together after the orchestrator discussion. 2026-10-04: The resolved [checkpoint test decision](../records/workflow-adaptation/decisions/01-checkpoint-test-authorship.md) replaced this choice. The implementing agent now writes tests test-first at the approved test seams the plan names, and the Specification review checks each requirement's test and the independence of its expected values. Check results still retain their observing actor and code revision.
17. When a requirement or dependency contract changes during the plan, the orchestrator first evaluates its impact and whether a human decision is needed. It considers existing authorization, uncertainty, alternatives, affected checkpoints, and consequences for completed work. Where a material choice remains, bring the user the impact, options, and a recommendation before affected implementation continues. Changes to goals or architectural boundaries retain the vision's human decision requirement. Previously authorized changes do not need repeated approval. Preserve earlier evidence, refresh affected context and gate expectations, and arrange reassessment once the response is settled. Unrelated work may continue. This records the user's refinement of Q18: a requirement change calls for judgment about human involvement, rather than automatic replanning.
18. The orchestrator proposes broader project guidance with its source and scope. The user approves that guidance before it becomes mandatory. Apply already approved relevant guidance and task-local corrections within agreed scope immediately. Supply later checkpoint agents with relevant guidance, without turning every retained observation into a requirement.
19. Use one implementing agent at a time for the first trial. Independent reviews and research may run in parallel. Revisit concurrent implementation after evaluating review effort and the clarity of revision-specific evidence. The user accepted choices 18 and 19 while refining choice 17.

## Existing constraints and observed gaps

[Recorded acceptance](../../docs/adr/0003-recorded-acceptance-for-readiness.md) concerns a whole work item and can remain valid for historical work after HEAD changes. [Orientation](../../docs/readers.md#recorded-acceptance) checks records and retained source hashes. It does not rerun tests, certify the current code, or authenticate a human approval. A checkpoint review needs to identify the code it actually examined.

Separate specs and plans fit [ADR 0001](../../docs/adr/0001-one-okf-bundle-per-project.md) and the [bootstrap tracker conventions](../../docs/agents/issue-tracker.md). Plain Markdown supporting documents currently live outside the OKF bundle and are explicitly linked. Their physical location does not change project ownership.

The current task-context reader includes whole documents linked directly from a ticket's Spec and Context sections. Acceptance snapshots those documents in full, so later progress edits inside a linked plan can stale acceptance. The ticket's Comments exclusion does not apply to a linked plan. Links inside that plan do not automatically select additional sources. A workflow must explicitly load separately stored progress and feedback unless reader selection is extended. These are constraints for the trial, not reasons to make ticket comments the primary store.

Separate files alone do not limit an implementing agent's context. Supplying a parent conversation that already contains the full plan would undermine the user's intended separation. The trial needs explicit context delivery and must not assume that the existing ticket-context reader already implements checkpoint selection.

The [task-context workflow](../../.agents/skills/task-context/SKILL.md) currently delivers all selected ticket sources in full. The reader accepts plain Markdown but requires its root and blockers to be inside the selected bundle. It follows blockers recursively and has no checkpoint filter. Selecting a checkpoint as a Context document does not expand that checkpoint's own links. A trial can give full ticket context to the orchestrator and separately assemble context for an implementing agent, with source identity retained. That is a proposed delegation procedure, not unchanged compliance with the current ticket implementation workflow. Limited supplied context does not restrict filesystem access.

The [implementation skill](../../.agents/skills/implement/SKILL.md) requests review before its final commit. The [review skill](../../.agents/skills/code-review/SKILL.md) specifies a comparison ending at HEAD. An uncommitted change can therefore fall outside that comparison. The trial must resolve this gap when defining the code covered by a review.

Sequential checkpoint delegation does not require a new implementation claim per checkpoint. The existing vision allows one active claim per work item, but it does not yet specify whether an orchestrator or an implementing agent holds that claim. Managed claims remain later product work. Check results, acceptance decisions, and human approvals retain their actual actors and revisions; orchestration does not replace that attribution.

The vision already requires durable handoffs, progress saved after meaningful decisions and checks, and inspection of current state before resuming. An orchestrator must therefore resume from project records and verify the current code, sources, and any still-running work before reusing prior results. A persisted completion marker alone cannot establish current verification or that a previous agent has stopped.

Checkpoint, orchestrator, and gate are now defined in the glossary. No new ADR is needed yet: the trial preserves the existing execution and acceptance boundaries, and its workflow choices remain reversible.
